# Архитектура помощника транскрибации

Система делится на четыре независимо развиваемых этапа. Общий идентификатор задания и версионированные manifests связывают артефакты, а каждый этап создает новую версию и не перезаписывает вход.

```text
1. recording.webm
   -> source.webm + transcript.html (S00...) + manifest v2
2. manifest v2
   -> evidence frames + speaker-attributed transcript
3. attributed transcript
   -> uncertain segments + audio excerpts + reviewed revision
4. reviewed revision
   -> meeting summary + decisions + action-item drafts
```

## Компоненты первой части

```text
Браузер пользователя
  │ регистрация / вход / загрузка WEBM / просмотр результата
  ▼
FastAPI
  ├── аутентификация ─────> users + sessions в SQLite
  ├── API заданий ────────> jobs в SQLite
  ├── потоковая загрузка ─> tmp/<job-id>/source.webm
  └── выдача файлов <────── jobs/<job-id>/transcript.html
                                  ▲
Очередь заданий ──> worker ──> noScribe через Windows ConPTY
```

FastAPI и worker работают в одном процессе Windows-службы. В один момент времени worker запускает не более одного noScribe. Состояние очереди хранится в SQLite, поэтому завершённые задания переживают перезапуск приложения.

## Этап 2: подпись активного говорящего

После завершения noScribe пользователь отдельно запускает атрибуцию, выбирает режим
и подтверждает передачу кадров. В быстром режиме worker группирует реплики по
уникальным голосовым меткам `S00`, `S01` и т. д., выбирает до трёх самых длинных
непустых реплик группы, объединяет их в один запрос и переносит найденную подпись
на всю группу. Из каждой реплики по умолчанию берутся два кадра около середины
интервала: это уменьшает риск попасть на переключение активного говорящего у края.
В точном режиме кадры
проверяются отдельно для каждой реплики. FFmpeg извлекает полные кадры, а выбранному
OpenAI-compatible провайдеру отправляются только JPEG-изображения. Vision-модель
ищет зелёную рамку в любом месте раскладки и читает видимую подпись плитки. При
трансляции своего экрана маленькая плавающая панель участников также считается частью
раскладки, даже если она находится поверх рабочего стола в углу кадра. Аудио,
текст транскрипции и API-ключ в результат не включаются.

Ответ валидируется локально и принимается при согласии кадров; конфликт даёт
`unknown`. Исходный `transcript.html` не изменяется. Результаты находятся в
`attribution/<run-id>/attribution.json` и `attributed-transcript.html`, а ручная
коррекция пользователя повторно публикует эти отдельные артефакты.

Таблица ручной коррекции повторяет гранулярность выбранного режима:
в быстром режиме показывается одна строка на уникальную `S`-метку и
исправление применяется ко всем её репликам; в точном режиме выводятся и
изменяются отдельные реплики. Локальный ручной запуск не отправляет кадры
внешнему провайдеру. При создании точной ручной версии после быстрого анализа
найденные подписи переносятся по исходным таймкодам, а пользователь уточняет их
для отдельных реплик без повторной оплаты модели.

Список заданий получает из SQLite последний запуск и последний успешно
опубликованный результат одним пакетным запросом. Поэтому перезагрузка браузера не
теряет рассчитанные подписи. Основная ссылка транскрипции ведёт на последний HTML с
подписями; исходный неизменяемый `transcript.html` остаётся отдельной ссылкой. Если
новый повторный запуск завершился ошибкой, ранее опубликованный результат продолжает
быть доступен.

Если Windows-служба перезапущена во время атрибуции, запуск возвращается в очередь.
Уже сохранённые назначения сегментов не пересчитываются, worker продолжает только с
оставшихся реплик и после завершения публикует итоговые HTML и JSON.

Административный контур разделён на общую статистику, расходы внешних моделей и
параметры. Каждый фактический запрос записывается в ledger с моделью, токенами,
числом изображений, статусом и подтверждённой стоимостью провайдера при её наличии.

Пользовательская сессия хранится в браузере как случайная `HttpOnly` cookie. В SQLite находится только SHA-256-хеш сессионного токена. Пароль пользователя хранится как `scrypt`-хеш. Все пользовательские API-запросы фильтруются по владельцу задания.

## Жизненный цикл задания

```text
загрузка во временный каталог
  -> queued
  -> running
  -> completed | failed
```

- `created_at` фиксируется после успешного приёма файла и постановки в очередь;
- `started_at` фиксируется, когда worker забрал задание;
- `completed_at` фиксируется и при успешном завершении, и при ошибке;
- неожиданно оставшееся `running` после перезапуска переводится в `failed` с кодом `service_restarted`.

## Хранилище первой части

```text
TRANSCRIPTION_DATA_DIR/
├── jobs.sqlite3
├── tmp/
└── jobs/
    └── <job-id>/
        ├── source.webm
        ├── transcript.html
        ├── manifest.json
        └── noscribe.log
```

Исходное имя записи хранится в SQLite и manifest только для отображения. Физические имена и каталоги формирует сервер. Клиент не может передать путь к файлу на сервере.

## Границы

- Этап 1 отвечает за прием файла, очередь, noScribe, первичную диаризацию `S00...` и выдачу HTML.
- Этап 2 извлекает кадры по таймкодам и сопоставляет нейтральные метки говорящих с участниками встречи.
- Этап 3 точечно перепроверяет сомнительные аудиоинтервалы другими моделями.
- Этап 4 один раз анализирует выбранную версию текста и готовит проверяемые итоги.

## Общие правила

- Пользователь входит по почте и паролю, а все задания и последующие артефакты принадлежат создавшему их пользователю.
- Локальная обработка и хранение используются по умолчанию.
- Перед внешней передачей аудио, кадров или текста требуется явное согласие.
- Все выводы сохраняют ссылки на исходный временной фрагмент.
- Низкая уверенность порождает отметку для проверки, а не выдуманное значение.
- Автоматически созданные задачи остаются черновиками до подтверждения человеком.

## Границы текущей реализации

- Реализованы этапы 1 и 2; этапы 3–4 зафиксированы отдельными спецификациями.
- Подтверждение почты, восстановление пароля и внешний сервис авторизации пока отсутствуют.
- Старые задания, созданные до появления владельцев, не назначаются пользователям автоматически.
- Автоматическое удаление старых записей и результатов пока отсутствует.
- Прямой HTTP допустим только в доверенной локальной сети или VPN; для других сетей требуется HTTPS.

Все параметры первой части описаны в [configuration.md](configuration.md), развертывание Windows-службы — в [windows-server-deployment.md](windows-server-deployment.md).

Подробные границы находятся в отдельных спецификациях `specs/002-*` — `specs/005-*`.
